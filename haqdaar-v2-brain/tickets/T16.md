# T16 · What the LOG must prove

**Type:** `wayfinder:grilling` (HITL) · **Module:** Data · **Blocked by:** ~~T09~~, ~~T10~~ · **Blocks:** T17
**Status:** **closed 8 Sep 2026** · map rev 16

## Question

The success bar says the LOG can prove why each scheme was chosen. What must it contain for that sentence to be true?

To resolve:

- The per-turn record: raw audio? transcript? confidence? the mask applied? the survivor count before and after?
- Enough to **replay** a call deterministically, or only enough to explain it? (Cross-call memory is out of scope, so nothing here serves a future call.)
- What is written when the model is discarded (QUESTION, NOISE, META) — anything at all?
- Retention **is already decided** (map rev 2): audio destroyed at hangup, decision trace persists, number hashed or not stored. What is left here is *what the trace must contain* to actually prove a choice, and whether anything in it is personal data despite the audio being gone.
- Who reads it, and in what format — a judge on 12 Sep is a different reader than an engineer debugging.

## Why it blocks

"Prove why" is in the acceptance bar. An unprovable claim on the day is a failed demo.

## Default if this stalls

Per-turn JSON lines: transcript, class, box, value, confidence, mask, survivors before/after; audio discarded at hangup; number hashed.

---

## Resolution

**The trace explains; it does not replay.** Four of the default's seven fields survive, and the two that most look like proof — the mask and the survivor counts — are exactly the ones that must not be stored.

### 1 · Replay or explain — explain, and the question answers itself

Retention was settled at map rev 2, before this ticket existed: audio is destroyed at hangup. Verbatim replay was therefore never on the table, and the branch is closed by a decision upstream of it rather than by argument here. What remains is the real requirement — a reader must be able to **reconstruct what happened and why, in text**, months later, without the caller and without the sound.

### 2 · The per-turn record — one JSON line per turn, every turn, regardless of class

```jsonc
// every turn
{ "turn_n": 3, "class": "ANSWER", "transcript": "<full English-hop utterance>" }

// ANSWER adds
{ "box": "state", "value": "BIHAR", "span": "in Bihar" }

// UNKNOWN value adds
{ "unknown_source": "declined" }        // declined | keypad_dropped

// Door A opener adds
{ "t_name": 3.4, "t_end": 17.9, "candidate_count": 1 }

// NOISE is thin
{ "turn_n": 4, "class": "NOISE" }
```

**Kept:**

- `turn_n`, `class` — one of ANSWER / CLARIFY / REPEAT / META / UNCLEAR / NOISE.
- `transcript` — **the full utterance, not just the extracted span.** This is the field that makes the four non-stamping classes provable instead of invisible. CLARIFY, REPEAT, UNCLEAR and NOISE write no box and no value; without the transcript, a judge or an engineer sees a turn that consumed budget and left no evidence of why. The span alone cannot do this job — a CLARIFY has no span.
- ANSWER-only: `box`, `value`, `span`. T11's span guard is **carried here, not re-derived** — the LOG records the span that passed the check, and does not re-run it.
- UNKNOWN-only: `unknown_source` — declined versus keypad-dropped (T11). Same value, different story, and only the LOG can tell them apart.
- Door A only: `t_name`, `t_end`, `candidate_count` (T12, rev 15).

**Struck:**

- `confidence` — has no source (T03) and was struck at T11, where echo-confirm replaced it. Nothing to log.
- `mask` and `survivors_before/after` — **T09 already settled this**: the snapshot id plus the ordered box vector reconstruct the entire call. Storing survivor sets would be a second copy of a derivable fact, which is redundancy dressed as proof. A reader who wants the survivors at turn 4 replays four AND instructions against a pinned snapshot and gets them exactly.

**The one exception to derive-don't-store: `ladder_rung`.**

Tally and specificity are cheap to recompute and stay derived (T10). Which stop condition closed the call — ≤4 survivors, the 8-turn cap, or zero-information — and which widening step ran on a dead end are different in kind. They are not properties of the state; they are **which branch the code took**, and re-running the algorithm months later to find out is trusting the thing under audit to testify about itself. Written once, at the moment it is true.

### 3 · The discarded classes — they all get a line

- **"QUESTION" in the ticket body is stale.** It is T04-era vocabulary for what T11 later split into CLARIFY and REPEAT. No separate handling; it falls out of the general schema.
- **META** is an ordinary turn under the schema above — class plus transcript.
- **NOISE gets a line even though it never reaches the model.** T11 has code catching the empty transcript before any model call, so there is nothing to record about a decision that was never made. But without the line, turn-count accounting is not auditable from the LOG alone: an 8-turn cap that fired after three visible turns reads as a bug rather than as five turns of a bad line. Thin — `turn_n` and `class` only — but present.

### 4 · No `terminal_state` field

A call that reaches a terminal state writes a closing line whose class and content say **which** one: scheme spoken plus door, dead-end with its ladder rung, keypad-only drop. A call that does not reach one simply stops mid-file. T04 already reads that structurally as *ended before a terminal state*, so a flag asserting what the file's shape already asserts is the same redundancy T09 avoided with survivor sets, and carries the same failure mode — a flag that disagrees with the trace is worse than no flag.

### 5 · The transcript is personal data, and that is a decision

Audio is gone at hangup, and the number is hashed. The transcript is neither, and it is the most identifying thing left. *"Scheduled Caste farmer in Bihar earning under ₹50,000"* is a caste, an income band and a state in one sentence, and it is **more identifying as persisted text than the hashed number sitting beside it**.

This is not new exposure — T20's widened scope already found the transcript this sensitive **in flight**. What is new is that T16 chooses to keep it **past hangup**, and that choice must be named rather than quietly absorbed by rev 2's *"the decision trace persists."* Recorded as a debt on the same footing as T08's suspended truth lock: an explicit, dated decision to accept exposure for 12 Sep, not a repeal of the concern.

Two consequences:

- **T20 gains its actual scope.** It no longer asks only whether the transcript may *transit* to a US-hosted model — it governs where the now-persisted transcript is allowed to **sit**. Storage location joins processing location as a T20 question.
- The redaction alternative was considered and rejected for 12 Sep: a redacted transcript cannot evidence a CLARIFY or an UNCLEAR, which is the entire reason the field exists. Redaction is a production question, not a demo one.

### 6 · Two readers, one file

T04 already requires pass/fail to be judged **structurally off the LOG alone**. A judge-only summary format would therefore be a second artifact that T04's own audit is not allowed to trust — and if it is trustworthy, it is derivable, and if it is derivable it should not be stored.

**One JSONL per call serves both readers.** A judge (or T04's audit) walks it top to bottom for terminal state, turn count and the spoken names. An engineer reads the same lines for class, box, value and span. No summary object is written — computed on read, same principle as tally and specificity.

## Handed downstream

- **T17** — loses its last Data blocker. The LOG's line schema is the Data module's outward interface for the trace; T17 freezes it.
- **T20** — scope widened a second time: **where the persisted transcript may be stored**, not only where it may transit.
- **T14** — NOISE writes a turn line, so whatever T14 decides counts as a turn against the 8-turn cap must be visible in the trace. The turn clock and the LOG's `turn_n` must agree.
- **T04** — reinforced, not amended: one file, judged structurally, no second format.
- **T18** — a keypad-only drop is a terminal state and writes a closing line like any other.

## Debt recorded

**The LOG persists caller-descriptive transcripts.** Accepted for 12 Sep; named, dated and owed. Nothing built for the demo may assume it stays acceptable.

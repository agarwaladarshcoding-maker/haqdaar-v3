# T19 · Where it runs on 12 Sep

**Type:** `wayfinder:task` (HITL) · **Module:** cross · **Blocked by:** ~~T20~~ *(edge cut 10 Sep, rev 24)* · **Decided 10 Sep 2026 · closes on the smoke call**

## Question

Scale is out of scope. Existence is not. Decide the minimum deploy target and prove a webhook from the outside world reaches our code.

Done when: a public HTTPS endpoint exists, responds inside the provider's webhook timeout, survives a restart, and holds the credentials for telephony, ASR and TTS without them living in the repo.

To settle while doing it:

- Where it runs, and whether that host sleeps when idle. A cold start on an inbound call is a dead call — this is the one scale-adjacent thing that is *not* deferrable.
- Where rendered audio files live and how the provider fetches them.
- How many simultaneous calls it can take before falling over — measured, not designed. One is an acceptable answer; not knowing the number is not.
- Who has deploy access on the day.

## Why it exists

"Industrial concerns later" is correct for autoscaling and wrong for having a machine. This ticket is the smallest possible version of having a machine.

## Default if this stalls

A single always-on small instance, no autoscale, audio served from the same host, secrets in environment variables, deploy access with Adarsh and one teammate.

## Resolution (decided 10 Sep, rev 24)

**The machine is Adarsh's laptop, behind a stable ngrok domain.** The default's "small instance" is overturned on the calendar, not on taste: a cloud VM is the right answer after 12 Sep, and two days before the demo it costs a deploy pipeline, a second copy of the ~200 MB snapshot, and an India-region pick that T20 has not answered. The laptop is where the build already runs, it satisfies all four done-when clauses, and it sits in Bengaluru — which **deletes T20's blocking edge by construction** (below).

This is a demo host, and it is written down as one. Nothing here is a production decision.

### What runs where

- **One process, one port** — Python 3.11 asyncio (T17). `/answer` is plain HTTP and returns the Stream XML; `/stream` is the WSS Plivo connects to. Same host, same port, so there is one URL to configure.
- **Public HTTPS/WSS: ngrok, free plan, the account's one dev domain.** It does not change on restart, so the Plivo Answer URL is set once and never edited again. The free-plan browser warning page only fronts HTML browser traffic, not Plivo's programmatic requests. This is also the setup Plivo's own audio-streaming guides use.
- **Rejected: Cloudflare quick tunnel** — new URL on every restart means a Plivo console edit on every restart, which is exactly when nobody has time. **Rejected for now: named Cloudflare tunnel** — needs a domain on Cloudflare; a fine post-demo move, not a 12 Sep errand.
- **Audio: nothing is served.** T15 already pushes audio down the socket — no URL, no fetch, no static host. The snapshot and rendered pool load into RAM at boot; `Corpus` raises at `load` (T17), so a broken snapshot fails when the process starts, never on a call.
- **Stream XML:**
  `<Stream bidirectional="true" audioTrack="inbound" keepCallAlive="false" contentType="audio/x-mulaw;rate=8000">wss://<dev-domain>/stream</Stream>`
  `keepCallAlive="false"` is T14's ratify-on-hardware ruling and gets ratified on the smoke call.

### The four done-when clauses, as checks anyone can run

| Clause | Check | Pass |
|---|---|---|
| Public HTTPS endpoint | `curl https://<dev-domain>/health` from a phone **on mobile data**, not the laptop's Wi-Fi | 200 |
| Inside webhook timeout | `/answer` returns static XML with no I/O; read the answer latency in Plivo's call debug log | well under a second |
| Survives a restart | kill process and tunnel, start both with one command, call again with **no Plivo console edit** | call connects, ≤60 s from kill |
| Credentials off the repo | `.env` in `.gitignore`; grep git history for key prefixes | nothing found |

### The one that is not deferrable: sleep

- **A sleeping laptop is the cold start.** Plugged in, lid open, OS sleep off for the whole demo window. Lid-close sleep on most laptops ignores "keep awake" utilities — the lid stays open.
- **Proof, not intention:** leave the laptop idle 30 minutes, then call. That call is the cold-start test, and it is the only one that counts.

### Concurrency: measured, not designed

- **Test:** three team phones dial within ten seconds of each other. Count how many reach the opener and complete cleanly. Write the number here: `max_concurrent_measured: __`.
- **The expected ceiling is Sarvam's concurrent streaming sessions on our plan, not the laptop** — one asyncio process doing an AND per turn is not the bottleneck. Check the plan limit and record it beside the measurement.
- **If the number is 1**, judges call one at a time, and that is announced before judging, not discovered during it.

### Three drills, each run once before 12 Sep

- **Wi-Fi dies.** Phone hotspot is the backup uplink. The ngrok agent reconnects on its own and the domain does not change. The in-flight call is lost; the next call must work. Pull the Wi-Fi, switch, call.
- **The process dies.** Run it under a restart loop, so a crash costs one call and a few seconds, not a person noticing.
- **The laptop dies.** A named teammate's laptop holds the same commit, the same built snapshot, the same `.env` and the same ngrok authtoken. **Cold switch only: stop the primary agent, then start the spare — never both.** Two agents on one domain either refuse to start or, if pooled, split traffic across two machines, and `/answer` landing on one laptop while `/stream` lands on the other is a dead call that looks like a code bug. Time the switch once.

### Deploy access on the day

- **Adarsh** (primary laptop) and **one named teammate** (spare). Nobody else touches either machine during judging.
- **Freeze during judging**: no `git pull`, no snapshot pointer flip. Rev 3's flip happens between sessions, never inside one.

### What stays open, on purpose

Hackathon-grade, and recorded so that none of it is mistaken for forgotten:

- **One machine, one uplink, no autoscale, no monitoring beyond the LOG.** Scale was ruled out at rev 2; this is its concrete shape.
- **ngrok free: 1 GB/month data out.** Outbound audio is base64 μ-law in JSON, roughly 11 kB/s, so ~40 MB per talking hour and ~25 hours of calls before the cap. Check the Usage page on the evening of 11 Sep; if more than half is gone, pay for a plan — a card, not a redesign.
- **No Plivo signature validation on `/stream` for 12 Sep.** Anyone who finds the URL can open a socket and spend our Sarvam and Gemini credit. Low odds over two days; first thing after the demo.
- **Personal data at rest on a personal laptop.** The LOG's persisted transcripts (T16's debt) sit on this disk. Full-disk encryption on is the whole control for 12 Sep.
- **T15's "runtime holds no TTS credentials" weakens to a code rule.** Sarvam is both Ear and Mouth, and to our knowledge one subscription key covers both, so the credential cannot be withheld from the runtime. For 12 Sep the runtime imports no TTS client, and a test asserts it. Named as the weakening it is; confirm in the Sarvam dashboard whether a scoped key exists.
- **After 12 Sep** — cloud VM in an Indian region, a named tunnel or real domain, signature validation. Not designed here.

### T20's edge is cut, not satisfied

- **The laptop is in Bengaluru.** Our side of the call audio sits in India by construction — which is T20's own stall default (*"an India-region deploy target"*) taken for free.
- **Deepgram is struck, not provisional.** T18 made ASR failure → keypad-only. There is no second ASR, so there is nothing US-hosted to rule on.
- **TTS is not call media.** It renders at build (T15), before any call exists — T20's own bullet.
- **The carrier question becomes empirical.** The smoke call streams India-region Plivo audio to our endpoint. If media anchoring binds the stream, Plivo refuses it on the first call today, not on 12 Sep.
- **Left in T20, blocking nothing:** the English-hop transcript text goes to Gemini outside India (T08). That is a data-protection question, not a carrier rule, and it cannot produce a dead number.

## Amended 10 Sep (rev 25) — Twilio first, behind the Audio seam

Adarsh decided: **build and demo on Twilio for now.** This is the explicit decision T05 said a slip past 5 Sep would require, taken in the open rather than by drift. **The laptop, the tunnel, the drills and the concurrency measurement all stand unchanged.** What changes is the provider end of the socket, and one argument about T20.

### What changes on the wire

- **Answer webhook** — the Twilio number's Voice URL points at `https://<dev-domain>/answer`, which returns:
  `<Response><Connect><Stream url="wss://<dev-domain>/stream"/></Connect></Response>`
  `<Connect><Stream>` is Twilio's bidirectional form. The stream URL takes no query string; per-call values go in `<Parameter>` children.
- **The T14 contract maps one-to-one**, so no design moves:

| Design term (Plivo names, T14/T15) | Twilio |
|---|---|
| `playAudio` | outbound `media` message (base64 μ-law 8 kHz, no header bytes) |
| `checkpoint` | outbound `mark` after the media |
| `playedStream` | inbound `mark` with the same name, when playback reaches it |
| `clearAudio` | outbound `clear` |
| `clearedAudio` | inbound `mark`s for every mark still queued at the clear — **Audio must remember a clear was sent, or a cleared mark reads as a played one** |
| DTMF on the socket | inbound `dtmf` event (inbound direction only — we never send DTMF) |
| `keepCallAlive="false"` | **dissolves by construction**: when the socket closes, `<Connect>` ends, no TwiML follows, the call ends. T14's ratify-on-hardware item is answered by the protocol |
| hang up after closing line | wait the closing line's `mark`, then close the socket |

- **Upgrade the Twilio account out of trial** before any outside caller dials — a trial account puts its own notice in front of the greeting, which breaks turn 0.
- **Webhook signature:** Twilio's `X-Twilio-Signature` is the equivalent of Plivo's. Still deferred past 12 Sep, as above.

### What changes about T20

- **"Call audio sits in India by construction" no longer holds.** On a Twilio +1 number, media passes through Twilio's US infrastructure before reaching the laptop.
- **The T20 edge stays cut, on different ground.** Media anchoring was a Plivo rule about a *domestic Indian call leg*. A caller dialling a +1 number makes an international call, so there is no domestic leg to anchor. It cannot produce a dead number.
- **New named debt:** caller audio transits the US for 12 Sep. It sits beside the Gemini transcript transit, and nothing is designed around either.
- **Latency:** the audio path now goes caller → US → Bengaluru → Sarvam → Bengaluru → US → caller. Expect a few hundred milliseconds more per turn than T14 assumed. The 1.2 s budget is ours and is measured from `vad.speech_end`, so it doesn't move — but the caller *feels* the transit. **Measure `t_name` on the smoke call rather than trusting T12's 3–5 s prediction.**

### What changes about the bar

- **"A live Indian number" becomes "a live number".** A judge on an Indian handset must be able to dial international. Many prepaid SIMs cannot, and those that can pay ISD rates. **Check each outside caller's handset before judging, not during it.**
- **Plivo is not dropped; it becomes a second adapter.** T17 froze Audio's outward interface as one settled turn, provider-neutral. If Udyam KYC lands before the demo, Plivo is about half a day behind the same seam and the Indian number returns to the bar. **Do not let a Twilio name leak past `audio/telephony/`** — T05's rev 3 warning is now live, not hypothetical.

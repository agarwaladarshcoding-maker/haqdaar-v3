## The one live item, and why the default beats the portal

The ticket's default read as a fallback:

> *Hand-cut an occupation list from the schemes' own eligibility prose and treat it as ours rather than myScheme's.*

Against rev 20 it is not a fallback. It is the better artifact, for three reasons:

- **T09 made the code the interface, not the label.** A box holds a code; Data owns the list and the code map; the Engine is language-blind. A portal's occupation label was always going to be re-coded by us on the way in.
- **T08 made the keyword list the offline test base.** ~150–200 values per language, frozen, so the inbound leg is testable against a table of utterances without a phone call. A list derived from the corpus is closed over exactly the corpus it must be tested against. A portal's list is not: it carries values no scheme in our corpus discriminates on, and those values are dead weight in the test table and dead mask columns in the build.
- **T06's build gate wants expressibility, not completeness.** A row that cannot be fully expressed does not enter the snapshot. Deriving the vocabulary from the prose the gate reads makes the two agree by construction instead of by reconciliation.

**What the default costs, stated plainly:** we can no longer say the occupation vocabulary came from the portal. That is a **provenance** claim, not a correctness one, and provenance is [T21](T21.md)'s question.

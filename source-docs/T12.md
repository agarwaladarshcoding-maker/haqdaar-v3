# ~~T12 · Door A: matching a spoken scheme name~~

**Type:** `wayfinder:grilling` *(retyped from `prototype` — see Resolution)* · **Module:** Model · **Blocked by:** — · **Closed 4 Sep 2026**

## Question (as written)

Build the cheapest possible version of the four in-memory searches and find out whether a real spoken scheme name actually matches.

To make concrete:

- A caller saying "PM Kisan", "पीएम किसान", "kisan wali yojana" and "that farmer scheme" — which of those should hit, and which should fall through to Door B?
- What the four searches actually are — exact, alias, fuzzy, embedding?
- The confidence threshold at which we confirm by naming rather than asking.
- Measure: does the read-back land inside the 20-second bar?

## Why it exists

Door A is claimed to fail cheaply into Door B. Nobody has ever seen it fail. Cheap to test, and it fails loudly if the alias table is thin.

## What was stale before the session started

Three of the four bullets could not be answered as written.

- **"the four searches — exact, alias, fuzzy, embedding."** Embedding died at T09 (1 Sep), which ruled out vector search because it cannot produce a trace and proving the choice is the LOG's second job. Four was already three.
- **"the confidence threshold at which we confirm by naming rather than asking."** Void. T11 (2 Sep) struck `confidence` from the model contract — a model scoring its own selection is a second generation, not evidence — and replaced it with unconditional echo-confirm. There is no number anywhere in the system to set a threshold on.
- **Type.** Filed `prototype` and blocked by T07. Only the *measurement* was ever blocked by T07. Everything else was design, unblocked, and sitting behind a corpus it did not need.

The fourth bullet — *nobody has ever seen Door A fail* — survived, and turned out to be the whole ticket.

## Resolution

### Door A is not a search stage. Door A is the opener.

The ticket assumed a router: hear the caller, decide which door, run a search behind door A. That shape is what generated four searches, a threshold, and a fall-through path to design.

**T11 already returns a list.** The opener call returns `(box, value, span)` triples — plural, unlike every question call, which returns exactly one. Adding one **`scheme` pseudo-box**, whose closed set is the corpus's scheme ids and whose match surface is the alias table, collapses the entire ticket into machinery that already exists:

- *"PM Kisan"* → `(scheme, PMKISAN, "PM Kisan")` → read-back.
- *"I'm a farmer in Bihar"* → `(occupation, farmer, …)`, `(state, bihar, …)` → Door B, seeded, exactly as T10 rev 14 already expects.
- *"that farmer scheme"* → no span matches any alias, the span guard drops it → Door B, seeded on `occupation=farmer`.

There is no routing decision, no second model call, and no extra turn. **"Fails cheaply into Door B" stops being a claim that needs testing and becomes a statement that there is nothing to fail** — it is one call, and the doors are just which fields came back. The ticket's stated fear (Door A's failure path has never been exercised) is answered by deleting the failure path, not by exercising it.

`scheme` is a **pseudo-box, not box 7.** It never enters the filter table, never gets a mask, is never asked as a question, and cannot be widened. It appears in the box vector for LOG reconstruction only.

### Two searches, not four

The span guard requires the span to be literally in the **transcript** — not to match an alias. So when the ASR writes *"PM kissan"*, the span passes and the model still selects `PMKISAN`. **Fuzzy matching is what the model is for**; it was never a stage. What survives:

1. **Exact alias string-match, in code, before the model.** Zero cost, and it is T08's offline test base — a table of utterances with no model in the loop.
2. **Model selection from the alias closed set.** Everything else, including every mis-hearing.

Rejected: fuzzy as a distinct stage (subsumed by 2); embedding (T09).

### Door A is exempt from echo-confirm — a deliberate narrowing of T11

T11 made echo-confirm **unconditional**. On Door A that costs a turn to say the scheme name, wait, and then say the scheme name again — comfortably 12–15 s of dead air before the first useful word, on a bar of 20.

**The read-back is the confirmation.** The name is the first thing spoken, and keypad interrupts everything always (rev 2). A caller who hears the wrong scheme hears it inside two seconds and presses a key.

T11's rule is narrowed to read: **echo-confirm is unconditional for box values.** The justification holds precisely there and not here — a wrong box stamp is silent, compounds through the ladder, and enters the LOG unchallenged, whereas a wrong scheme is loud and self-correcting. Confirming a name and then immediately saying the name is a wasted turn with no error it can catch.

### The 20-second clock: stamp both, judge one

Nobody had ever pinned where the bar starts and stops, which meant a demo could pass or fail on a definition rather than on the system. Both readings are stamped in every Door A call:

- **`t_name`** — end of the caller's utterance to the **first word of the scheme name.**
- **`t_end`** — end of the caller's utterance to the **last word of the `summary`.**

**The bar is judged on `t_name`.** Everything before the name is dead air; everything after is content the caller asked for, and they know they have been heard the moment the name lands. `t_end` is recorded but cannot fail the bar — it exists so that Marathi `summary` length becomes evidence for free rather than a surprise on 12 Sep.

Predicted `t_name` budget: ASR finalisation + one model call (~50–100 ms, T11) + content-addressed cache fetch. **No TTS in the path** — T06's `summary` is pre-rendered. This should land at 3–5 s, which makes the bar uninteresting, which is the honest result and worth putting on record before T12b measures it.

### Ambiguity: candidate count decides, and the data decides the count

*"kisan wali yojana"* plausibly matches PM-KISAN, Kisan Credit Card, and whatever else carries the word. Guessing one risks an untruth; sending it to Door B spends six questions on a scheme the caller already named.

- **1 candidate** → Door A, read it.
- **2 candidates** → **one keypad turn naming both** ("press 1 for X, press 2 for Y").
- **3+ candidates** → Door B, seeded with whatever the name implies (typically `category`).

The 2-candidate turn adds no machinery: the exact-alias code pass already produces a *set*, so counting it is free, and "a keypad question over a closed set of two" is the exact shape every box question already has under T10. It costs 1 turn against Door B's six.

Capped at 2 because reading three scheme names aloud costs more time than Door B's first question, and at 3+ filtering genuinely beats naming.

Rejected: send every ambiguity to Door B. Simpler, and correct if the alias table were rich — but T12's own premise is that it is thin, so ambiguity will be the common case and paying six questions for it is the expensive answer.

### The four test utterances, answered

| Utterance | Result | Why |
|---|---|---|
| "PM Kisan" | **Hit** | exact alias, code pass, no model |
| "पीएम किसान" | **Hit** | exact alias — aliases are trilingual (T06) |
| "kisan wali yojana" | **2 candidates → keypad; 3+ → Door B** | resolved by the alias uniqueness gate below, not by code |
| "that farmer scheme" | **Miss → Door B, seeded `occupation=farmer`** | no alias span; the span guard drops it. This is the case that proves seeding works |

### What T12 hands T07 (the alias field contract)

T06 made aliases a first-class field. Nobody had said what goes in it. This is T12's output and it is an **input T07 needs**, which is why the dependency runs the other way from how the ticket was filed.

- **Shape:** per language (en/hi/mr), a list of strings stored **as spoken**, lowercased and whitespace-normalised at build. Honorifics and filler are kept in the stored alias, never stripped at query time.
- **Minimum three per language per scheme:** the official short name, the common spoken contraction, and the bare-noun form. The official title is stored separately and does not count toward the three.
- **Uniqueness gate at build:** an alias string appearing on **≥3 schemes is dropped from all of them** — it is a category word, not a name (*"yojana"*, *"scheme"*, *"sarkari"*). An alias appearing on **exactly 2 is kept**, and those two schemes *are* the keypad disambiguation pair. **Branch 3 therefore falls out of the data, not out of code** — no ambiguity list is authored or maintained anywhere.
- **Build gate:** a scheme with fewer than three usable aliases in any language does not enter the snapshot, consistent with T06's rule that a row which cannot be fully expressed is excluded rather than half-loaded. Named as a dial: if this shrinks the 12 Sep corpus, lower the floor rather than admitting a scheme the caller cannot name.

### Prompt cost of the alias set

The `scheme` pseudo-box adds ~3 aliases × N schemes to the opener prompt — but **only the call's language slice is loaded**, since T08 pins language per call. At the demo corpus size that is a few hundred short strings, on the order of 1,500 tokens, against T11's whole-demo estimate of ~40,000. It is an opener-only cost; question calls carry no alias set at all.
